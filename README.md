# 标书初稿流水线 · Tender Bid Drafter

一份招标文件 → 四份能直接派活的产物。给企业服务类投标的商务团队用。

> 它不是"AI 写标书"。它把招标文件里那些**藏在第三章资格条件里的 ★ 条款、散落三章的格式要求、格式各家不同的评分表**拆成清单，让你在动笔之前就知道：钱在哪、哪分是硬丢分、还缺什么材料。

![icon](./_icon.png)

---

## 它做什么 / 不做什么

| 做 | 不做 |
|---|---|
| 抽评分点，对齐"声明总分 vs 实拆总分" | 不填报价，一个数都不猜 |
| 抽 ★/▲ 实质性条款与废标红线 | 不盖章、不代签、不拟资格承诺函 |
| 从材料库匹配对应材料，标出过期 | 不判定资格是否合格 |
| 生成四册目录初稿（含建议篇幅） | 不产出标书正文 |
| 出递交前自查清单（逐条打勾） | 不保证评分表是图也能读 |

**一句话边界：抽取、匹配、骨架。判断和签字都是人的事。**

## 示例跑通的结果

用仓库自带的示例招标文件（虚构的"滨江市人社局运维服务"，含 ★ 条款、两张评分表、废标章节）：

```
$ python scripts/run_pipeline.py assets/sample/招标文件_智慧人社运维_示例.md \
      assets/material_library.example.json -o ./out
```

| 产物 | 实拆结果 |
|---|---|
| 评分点 | **11 个，合计 100.0 分**（与声明总分一致）｜客观 55 / 主观 15 / 报价 30 |
| 实质性条款 | ★ 5 条 ｜ 废标红线 13 条 ｜ 格式要求 11 条 ｜ 资格条款 8 条 ｜ 时间节点 5 个 |
| 材料匹配 | 19 条需求：已覆盖 11 / 需改写 7 / 缺口 0 / 待报价 1<br>评分 100 分中：已覆盖 33 分、需改写 37 分、待报价 30 分 |
| 有效期预警 | 3 条（含一份**已过期 87 天**的证书） |
| 目录初稿 | 四册 32 章 |

跑出来的真实产物在 [`examples/`](./examples)，先看效果再决定要不要装。

## 快速开始

### 作为 WorkBuddy Skill

```bash
git clone https://github.com/<你的用户名>/tender-bid-drafter.git \
  ~/.workbuddy/skills/tender-bid-drafter
```

重启客户端，输入框敲 `/` 找「标书初稿流水线」，或直接说"这份招标文件帮我拆评分点"。

依赖只有 Python 3.7+ 标准库，**不需要 pip install 任何东西**。

### 纯命令行

```bash
python scripts/run_pipeline.py <招标文件> <材料库.json> -o <输出目录>
```

支持 `.md` / `.txt` / `.docx`。**不支持 PDF**——八成招标文件是 PDF，这条先看清楚，见下方"已知局限"。

分步跑（中途可手改中间件）：

```bash
python scripts/tender_parse.py      招标文件.docx -o parsed.json
python scripts/material_match.py    parsed.json 材料库.json -o matched.json
python scripts/render_deliverables.py parsed.json matched.json -o ./out
```

`parsed.json` 可以手改。评分表被合并单元格吃了、编号识别歪了，改这个文件再跑后两步，不用从头解析。

## 产物

```
out/
├── parsed.json          # 中间件：招标文件结构化结果（可手改）
├── matched.json         # 中间件：匹配结果 + 全库有效期扫描
└── output/
    ├── 01_评分点清单.md / .csv   # 分值、主客观、评分标准原文、原文行号
    ├── 02_材料匹配表.md          # 每条需求配哪份材料、状态、有效期预警
    ├── 03_目录初稿.md            # 四册章节 + 对应评分点 + 拟用材料 + 建议篇幅
    └── 04_自查清单.md            # A 废标红线 / B ★条款 / C 形式 / D 时间 / E 覆盖度 / F 人工复核 / G 有效期
```

**每条都带原文行号**（`L69` 这种）。不是装饰——是为了让你三秒回原文，验证它有没有胡说。

## 材料库

复制 [`assets/material_library.example.json`](./assets/material_library.example.json) 改。最小可用 10 条。

```json
{
  "id": "M-003",
  "name": "信息系统安全等级保护备案证明（三级）",
  "type": "qualification",
  "covers": ["等级保护", "等保三级", "信息系统安全"],
  "valid_until": "2027-05-31",
  "path": "资质/等保三级.pdf"
}
```

**`covers` 是整条链路的命门。** 里面要抄招标文件的原话——尤其带"200 万""三级""近三年"这类限定词的。写得潦草，匹配结果就全是"需改写"，然后你会以为是代码有问题。

有效期字段别偷懒不填。全库扫描会主动暴露 60 天内到期和已过期的证书，**跟这份材料有没有被匹配到无关**。

## 设计原则

**一、脚本只做机械活，判断全留给人。** 报价输出"待报价（人工决策）"；匹配到营业执照不等于满足"注册资本 1000 万"。

**二、抽不到就报空，不编。** 宁可写"未解析到评分表，须人工补录"，也不补一条看起来合理的假评分点。投标这行，漏一条真条款比多十条假条款危险得多。

**三、"部分覆盖"才是核心价值。** 企业资质 8 分里有 4 张证，你只有 2 份材料——这就是漏项的源头。判"已覆盖"等于帮你把雷埋好。

## 已知局限

诚实列出来，别装没这回事：

| 局限 | 后果 |
|---|---|
| **完全不解析 PDF** | 直接报错退出。先转 Word 或导出文本 |
| 评分表是图片 / 扫描件 | 输出 0 分并报警，不编造 |
| 评分表列头用的是"标准分 / 评分细则" | 已做模糊匹配，但极端写法仍可能整表丢弃 |
| 实质性条款用 `*` `※` 或裸"必须" | 可能只抓到一部分，漏掉的只会出现在 warnings 里 |
| 资格条款用「（一）（二）」编号 | 部分形态会漏抽 |
| 分值列合并单元格 | 合计对不上总分，需手改 `parsed.json` |
| 材料匹配是**字面相似度**，没有语义 | "ISO27001"和"ISO9001"字面上像，它就敢配 |
| 一章内多个评分表 | 只认第一个带分值列的表 |

**跑完先看 warnings，不要只看产物。** 警告变多说明这份文件里有它没认出来的东西，不是它坏了。

## 必须人工接手的

| 环节 | 为什么 |
|---|---|
| **报价** | 价格分通常 30 分起。模型不知道你的成本、税率、有没有第三方分钱 |
| **签字 / 盖章 / 骑缝 / 密封** | 法律行为，不是格式问题 |
| **资格实质性判断** | "已覆盖"只说明库里有材料，不说明你够格：注册资本、证书等级、认证范围、合同金额、时间区间、在职状态，逐项核 |
| **废标红线确认** | A 区 13 条必须由**没参与写标书的人**逐条打勾。自己查自己，眼里只有"我写得挺好" |

